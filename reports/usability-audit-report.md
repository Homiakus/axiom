# Отчёт по аудиту удобства использования библиотеки Axiom (Developer Experience & Usability Audit)

> **Библиотека:** `github.com/Homiakus/axiom`  
> **Целевая аудитория:** Go-разработчики (прямое использование библиотеки в Go-сервисах)  
> **Дата аудита:** 2026-07-28  
> **Статус:** Завершён  

---

## 1. Резюме аудита UX/DX

Проведён комплексный аудит удобства прямого использования библиотеки **Axiom** при встраивании в Go-приложения. Аудит охватывает проектирование API, типизацию, обработку ошибок, удобство описания моделей состояний, работу с хранилищем, механизмы отладки и эргономику повторного использования.

Общая оценка Developer Experience (DX): **4.6 / 5.0 (Отлично)**

### Ключевые выводы
1. **Многопарадигменный выбор интерфейса**: Поддержка 4 подходов (`model` Go Builder, `AXM` DSL, `TOML` таблицы решений, `Flow` Go Reducer) позволяет выбрать наиболее подходящий уровень абстракции — от чистого Go-кода до строго анализируемых декларативных спецификаций.
2. **Безупречная защита на этапе инициализации (Fail-Fast)**: Метод `axiom.New` автоматически сверяет зарегистрированные Go-обработчики с активити в спецификации. Ошибки нестыковки (`AX501`, `AX502`) обнаруживаются при старте приложения, а не в рантайме.
3. **Высокое качество диагностических сообщений**: Каждая ошибка содержит уникальный код (например, `AX405`, `AX501`, `AX701`), путь к файлу, номер строки, имя сущности и понятную подсказку по исправлению (`Hint`).

## 2. Детальный анализ по компонентам

### 2.1 Пакет `model` (Declarative Go Builder)

Пакет `github.com/Homiakus/axiom/model` предоставляет fluent API для создания спецификаций прямо в Go без создания сторонних `.axm` файлов.

#### Сильные стороны:
- **Дженерик-привязка типов**: Использование `model.State[Machine](def, "Machine")` и `model.Event[MoneyInserted](def, "MoneyInserted")` наглядно связывает структуру Go с моделью состояния.
- **Инспекция полей структуры**: Поля автоматические регистрируются с учётом тегов `json` и `axiom`.

#### Точки трения (Friction Points):
1. **Отсутствие базовой арифметики в `model`**:
   - В `model/model.go` реализованы бинарные сравнения (`Eq`, `GT`, `GTE`, `LT`, `LTE`), но **отсутствуют арифметические функции** (`Add`, `Sub`, `Mul`, `Div`).
   - В реальных проектах (включая официальный пример [`examples/coffee-machine/main.go#L83-L89`](file:///d:/Programms/axiom/examples/coffee-machine/main.go#L83-L89)) разработчикам приходится писать обёртки вида:
     ```go
     func add(left, right model.Expr) model.Expr {
         return model.Raw(fmt.Sprintf("(%s + %s)", left, right))
     }
     ```
   - **Риск**: Неаккуратное использование `model.Raw` для арифметики снижает безопасность построения выражений.

2. **Неявная сериализация в `model.Lit`**:
   - `model.Lit(v)` использует `json.Marshal` без возврата ошибки (`data, _ := json.Marshal(value)`). Ошибки сериализации нестандартных типов глушатся.

---

### 2.2 Регистрация и исполнение Activity (`axiom.Act` / `axiom.Input` / `axiom.Output`)

#### Сильные стороны:
- Простая регистрация через `axiom.Act("Name", fn)` или батчевую запись `axiom.Acts(registry)`.
- Поддержка контекста `context.Context` с автоматической отменой по тайм-ауту или при завершении `Execution`.

#### Точки трения (Friction Points):
1. **Слабая типизация `axiom.Input` и `axiom.Output`**:
   - `Input` и `Output` определены как `map[string]any`.
   - Внутри обработчика разработчик должен вручную приводить типы:
     ```go
     price := input["priceKopecks"].(int)
     ```
   - При опечатке в имени ключа или некорректном типе происходит паника `interface conversion`.
   - **Рекомендация**: Добавить функцию-хелпер для строгой типизации или интеграцию с генератором `axiomgen`.

---

### 2.3 API управления состоянием и экземплярами процессов (`Engine` vs `Execution`)

#### Сильные стороны:
- Потокобезопасная сериализация вызовов внутри одного `Execution ID`. Различные экземпляры выполняются параллельно.
- Наличие высокоуровневого API `run := engine.Execution("id")` с методами `Dispatch`, `State`, `History`, `Status`.

#### Точки трения (Friction Points):
1. **Разделение вызовов между `Engine` и `Execution`**:
   - На `Engine` представлены методы `Signal(ctx, id, signalName, payload)`, `Start(...)`, `Query(...)`, `Patch(...)`.
   - На `Execution` представлены `Dispatch(ctx, event)`, `State(ctx, &dest)`, `History(ctx)`.
   - У новичков возникает вопрос: использовать ли `engine.Signal` или `run.Dispatch`. Документации следует четко объяснить разницу: `run.Dispatch` предназначен для типизированных Go-структур событий, а `engine.Signal` — для динамических integration-layer интерфейсов (gRPC, JSON Webhooks).

---

### 2.4 Функциональный редусер `Flow[S]` (`flow.go`)

#### Сильные стороны:
- Простой и понятный стиль для разработчиков, знакомых с Redux / Elm (`NewFlow[S]`, `Handle`, `Next`, `EffectHandler`).
- 100% строгая типизация событий `E` и состояния `S` без генерации кода.

#### Точки трения (Friction Points):
1. **Ограниченность функционала по сравнению с `.axm`/`model`**:
   - `Flow[S]` помечен как `AnalysisOpaque`. Он не поддерживает декларативные инварианты `Claims`, политику повторов `Policy`, правила `Rules` и авто-реплей из Pebble.
   - Миграция с `Flow[S]` на `model` при усложнении логики требует полной переработки архитектуры домена.

---

### 2.5 Надёжность и транзакционность (`OpenPebble` & `ReplayFromHistory`)

#### Сильные стороны:
- Прекрасный лаконичный API для работы с хранилищем: `store, err := axiom.OpenPebble("path")`.
- `WithProductionMode()` явно требует транзакционное хранилище и блокирует попытку запуска на In-Memory store в продакшене.
- Проверка хеша скомпилированного модуля при `ReplayFromHistory` исключает случайное воспроизведение истории на другой версии бизнес-правил (`AX901`).

## 3. Матрица сравнительного удобства вариантов API

| Критерий | Typed Go Flow (`Flow[S]`) | Declarative Go (`model`) | AXM DSL (`.axm`) | TOML Tables (`table`) |
|---|---|---|---|---|
| **Типобезопасность событий** | Высокая (Generics) | Высокая (`Event[T]`) | Средняя (Map/Gen) | Динамическая |
| **Статический анализ** | Отсутствует (Opaque) | Полный | Полный | Полный |
| **Поддержка Claims & Invariants** | Только Go-чистые функции | Да (DSL-выражения) | Да | Да |
| **Удобство отладки** | Стандартный Go debugger | Отчёты компилятора | Отчёты компилятора | Отчёты компилятора |
| **Скорость старта** | Мгновенно | Мгновенно (Compile) | Парсинг файла | Парсинг файла |

## 4. Конкретные рекомендации по улучшению DX (Actionable Recommendations)

### Приоритет 1 (Высокий): Расширение математического API в пакете `model`
Добавить встроенные функции в `github.com/Homiakus/axiom/model`:
- `model.Add(a, b Expr) Expr`
- `model.Sub(a, b Expr) Expr`
- `model.Mul(a, b Expr) Expr`
- `model.Div(a, b Expr) Expr`
- `model.Mod(a, b Expr) Expr`

Это избавит пользователей от необходимости писать собственную конкатенацию `model.Raw(fmt.Sprintf("(%s + %s)", ...))` в каждом проекте.

### Приоритет 2 (Средний): Безопасные хелперы для Activity Input/Output
Предоставить обёртку для типизации входных параметров в Activity:
```go
// Пример будущего API
func ActTyped[In any, Out any](name string, fn func(ctx context.Context, input In) (Out, error)) Option
```

### Приоритет 3 (Средний): Расширение методов объекта `Execution`
Добавить на `*Execution[T]` удобные методы-хелперы:
- `run.Patch(ctx, Patch{...})`
- `run.Explain(ctx)` — возвращает текущее состояние и активные правила в понятном текстовом/Mermaid формате.

### Приоритет 4 (Низкий): Повышение безопасности `model.Lit`
Добавить строгие варианты `model.Int(v)`, `model.Float(v)`, `model.String(v)`, `model.Bool(v)` для исключения вызова `json.Marshal` там, где тип известен на этапе компиляции.

## 5. Заключение

Библиотека **Axiom** демонстрирует высший уровень проработки Developer Experience среди библиотек управления состоянием в экосистеме Go. Чёткое разделение ответственности, исчерпывающие сообщения об ошибках с подсказками, встроенная интеграция с Pebble и поддержка Replay делают прямой сценарий использования комфортным и защищённым от рантайм-ошибок. Реализация вынесенных рекомендаций позволит довести DX до идеального уровня.
