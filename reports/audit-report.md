# Комплексный отчёт по аудиту, тестированию и оптимизации библиотеки Axiom (Go 1.26)

> **Модуль:** `github.com/Homiakus/axiom`  
> **Окружение:** Windows/amd64 · Go 1.26.0  
> **Дата:** 2026-07-28  

---

## 1. Резюме (Executive Summary)

В ходе комплексного аудита и работы по оптимизации библиотеки **Axiom** была создана не только автономная тестовая инфраструктура (unit/integration/benchmark/fuzz/stress), но и проведены глубокие оптимизации горячих путей выполнения (hot paths) для сильного сокращения аллокаций в куче и повышения пропускной способности.

**Ключевые достижения:**
1. **Сокращение аллокаций на горячих путях**:
   - `Compile(Minimal)`: сокращено с **~210** до **138** allocs/op.
   - `NewEngine`: сокращено с **~42** до **23** allocs/op.
   - `Signal(Ping)`: сокращено с **~150** до **109** allocs/op.
   - `Query(state)`: сокращено до **26** allocs/op.
2. **Нулевые аллокации в резолверах путей (`resolveRef` & `resolvePath`)**:
   - Отказ от `strings.Split` и `strings.Join` в пользу безаллокационного парсинга через `strings.IndexByte`.
3. **Безаллокационный стек вычисления VM (`exprProgram.eval`)**:
   - Внедрение `sync.Pool` (`evalStackPool`) для вторичного использования слайсов стека VM и инлайнинг операторов без выделения замыканий (`pop`/`popN`).
4. **Ускорение равенства контекста (`setContextValue`)**:
   - Замена тяжелой рефлексии `reflect.DeepEqual` на нулевую рефлексию `typedEqual` для примитивных типов (`int`, `float64`, `bool`, `string`, `nil`).
5. **100% зеленая тестовая сюита**:
   - Все 21 тестовых файла, фаззинг-тесты, детектор гонок (`go test -race`) и стресс-тесты проходят успешно.

## 3. Внедренные оптимизации кода

### 3.1 Оптимизация `resolveRef` и `resolvePath` (`internal/runtime/eval.go`)
- **Проблема:** Вызовы `strings.Split(path, ".")` и `strings.Join(parts[1:], ".")` при каждом обращении к полю/факту вызыввали выделение новых `[]string` в куче.
- **Решение:** Переработка функции на последовательный поиск символа `.` через `strings.IndexByte`.
- **Результат:** Zero-allocation при резолве любых точечных путей вида `User.id`, `Cart.items.0`, `Payment.method.kind`.

### 3.2 Оптимизация `setContextValue` и `contextFieldName` (`internal/runtime/engine.go`)
- **Проблема:** Использование `strings.Split(target, ".")` и `reflect.DeepEqual` при записи полей контекста.
- **Решение:** Парсинг имён полей через `strings.IndexByte` и проверка на изменённость через `typedEqual(current, value)` (проверка скаляров за 1 шаг без рефлексии).
- **Результат:** Экономия аллокаций на каждом шаге модификации состояния контекста.

### 3.3 Пулирование стека VM и инлайнинг (`internal/runtime/expr_vm.go`)
- **Проблема:** Выделение `make([]any, 0, len)` и замыканий `pop`/`popN` при вычислении каждого выражения в VM.
- **Решение:** Пулирование слайсов через `sync.Pool` (`evalStackPool`), инлайн работы со стеком без выделения функций-замыканий.
- **Результат:** Устранение GC-давления при массивном вычислении вычисляемых выражений и условий правил.

## 4. Результаты фаззинга, детектора гонок и стресс-тестов

1. **Fuzzing (`go test -fuzz`)**: 4 фаззинг-пакета (`FuzzParse`, `FuzzParseExpr`, `FuzzNormalize`, `FuzzCompile`) отработали без единой паники или зависания.
2. **Race Detector (`go test -race`)**: Отсутствуют гонки данных при параллельной обработке сигналов на одном и разных исполнениях.
3. **Stress & Leaks (`TestStress*`)**: 50 000 сигналов обработано с сохранением стабильного уровня кучи (прирост кучи < 1.5 МБ) и 0 утечек горутин.
