Да. По коду видно, что библиотека уже идёт в правильную сторону: у вас есть `fastPlan`, `bitset []uint64`, индексы `signalRules`, `fieldRules`, `atomRules`, `atomDeps`, компиляция условий в `required/forbidden` битовые маски и fast-runtime режим. Но сейчас горячий путь всё ещё сильно смешан с `map[string]any`, строковыми lookup, `reflect.DeepEqual`, аллокациями и недетерминированным runtime-состоянием.

Ниже — перечень улучшений в порядке максимальной отдачи.

## Целевая архитектура

Лучший вариант для этой системы:

```go
compiled module:
  fieldID     uint32
  atomID      uint32
  ruleID      uint32
  signalID    uint32
  activityID  uint32

execution state:
  activeAtoms bitset
  boolFields  bitset
  present     bitset
  dirtyFields bitset
  values      map[FieldID]Value
  factValues  map[AtomID]map[FieldID]Value
```

То есть строковые имена остаются в compiler/debug/API, а runtime работает почти полностью через `uint32` ID.

---

# P0 — самое важное

## 1. Убрать `fastPlan.states map[string]bitset`

Сейчас состояние атомов хранится внутри `fastPlan`:

```go
states map[string]bitset
```

и извлекается по `execution.ID`. Это опасно: состояние fast-runtime не является частью `Execution`, не сохраняется в store, может протухнуть, потеряться при рестарте процесса и разойтись со snapshot/history.

Нужно перенести состояние в `Execution`:

```go
type Execution struct {
    ...
    ActiveAtoms []uint64
    Present     []uint64
    BoolValues  []uint64
    Values      map[FieldID]Value
}
```

Это приблизит систему к Temporal-подходу: состояние должно быть восстановимо из истории или snapshot, а не жить в памяти плана.

---

## 2. Сделать replay настоящим event-sourcing replay

Сейчас `Replay` фактически делает `GetExecution` и `recomputeFast`, то есть не проигрывает историю событий заново.

Для надёжности ближе к Temporal нужно:

```text
History -> deterministic replay -> Execution state
```

История должна быть источником истины:

```go
ExecutionStarted
SignalReceived
ContextPatched
ActivityScheduled
ActivityCompleted
ActivityFailed
TimerFired
ExecutionCompleted
```

Сейчас history уже пишется в `Start`, `Signal`, `Patch`, `completeActivity`, но она не используется как основной механизм восстановления.

Нужно добавить:

```go
func ReplayFromHistory(module *CompiledModule, history []HistoryEntry) (*Execution, error)
```

и тест:

```go
liveState == replayedState
```

Это один из главных шагов к надёжности уровня workflow engine.

---

## 3. Заменить `map[string]map[string]any` на ID-based state

Сейчас `Execution` хранит:

```go
Context  map[string]map[string]any
Computed map[string]any
Facts    map[string]FactValue
```

а `FactValue` внутри тоже держит `map[string]any`.

Это удобно, но для 1 млн условий и быстрого runtime это слабое место.

Лучше:

```go
type Value struct {
    Kind ValueKind
    I64  int64
    F64  float64
    S    string
    B    bool
    Any  any // только escape hatch
}

type ExecutionState struct {
    ActiveAtoms bitset
    Present     bitset
    BoolValues  bitset
    DirtyFields bitset
    Values      map[uint32]Value
}
```

Для bool-полей:

```text
present[fieldID] = значение существует
boolValues[fieldID] = true/false
```

Для не-bool значений:

```text
values[fieldID] = Value
```

Это даёт O(1) доступ по ID и сохраняет вашу идею: битовая маска для активности, map только для детальных значений.

---

## 4. Убрать строки из hot path

Сейчас в runtime много строковых lookup:

```go
fieldRules map[string]bitset
signalRules map[string]bitset
atomsByName map[string]int
ruleIDs map[string]int
```

Это нормально для компилятора, но не для исполнения.

На этапе компиляции нужно построить таблицы:

```go
FieldName -> FieldID
SignalName -> SignalID
RuleName -> RuleID
AtomName -> AtomID
```

А в runtime использовать:

```go
fieldRules []bitset // fieldID -> rule bitset
signalRules []bitset // signalID -> rule bitset
atomRules []bitset // atomID -> rule bitset
atomDeps []bitset // atomID -> dependent atom bitset
```

Тогда dispatch становится почти таким:

```go
dirtyRules := bitset{}
for fieldID := range dirtyFields.Iter() {
    dirtyRules.Or(plan.fieldRules[fieldID])
}
```

---

## 5. Переписать `bitset.ids()` без аллокаций

Сейчас `ids()` каждый раз создаёт `[]int` и сканирует все 64 бита каждого слова.

А в `recompute` это используется особенно дорого:

```go
for len(dirty.ids()) > 0 {
    ids := dirty.ids()
    ...
}
```

То есть на каждой итерации вы дважды аллоцируете и сканируете dirty bitset.

Нужно сделать итератор через `math/bits`:

```go
func (b bitset) ForEach(fn func(id int)) {
    for wordIdx, word := range b {
        for word != 0 {
            bit := bits.TrailingZeros64(word)
            fn(wordIdx*64 + bit)
            word &= word - 1
        }
    }
}
```

И заменить:

```go
for len(dirty.ids()) > 0
```

на:

```go
for !dirty.Empty()
```

Это даст большой прирост без изменения архитектуры.

---

# P1 — скорость ближе к O(1)

## 6. Сделать `changed` битовой маской, а не `map[string]struct{}`

Сейчас dirty/change-set передаётся как:

```go
map[string]struct{}
```

и затем преобразуется через строковые ключи.

Нужно:

```go
type ChangeSet bitset
```

или:

```go
type Dirty struct {
    Fields bitset
    Atoms  bitset
}
```

Тогда `Patch`, `applyWrites`, `completeActivity` должны возвращать не `[]string`, а компактный `bitset`.

Для внешнего API можно оставить строки:

```go
Patch(map[string]any)
```

но сразу на входе преобразовывать в `fieldID`.

---

## 7. Precompiled expression VM вместо recursive `evalExpr`

Сейчас `evalExpr` рекурсивно ходит по AST, использует `any`, `reflect.DeepEqual`, `strings.Split`, `resolvePath`, `fmt.Sprint`, `json.Marshal` для hash и т.д.

Нужно компилировать выражения в bytecode/ops:

```go
type OpCode uint8

const (
    OpLoadField OpCode = iota
    OpLoadConst
    OpExists
    OpEqInt
    OpEqString
    OpGtInt
    OpAnd
    OpOr
    OpReturn
)

type Instr struct {
    Op OpCode
    A  uint32
    B  uint32
}
```

Тогда выражение:

```axiom
User.id exists and User.email exists
```

становится:

```text
LoadField User.id
Exists
LoadField User.email
Exists
And
Return
```

А не каждый раз парсится через строковые пути.

---

## 8. Специализировать сравнения по типам

Сейчас `==` и `!=` используют:

```go
reflect.DeepEqual(left, right)
```

Это удобно, но дорого и не всегда желательно для детерминированного workflow.

Лучше на compile stage знать типы:

```go
EqBool
EqInt
EqFloat
EqString
EqTime
```

и выполнять прямое сравнение:

```go
return left.I64 == right.I64
```

`reflect.DeepEqual` оставить только для редкого escape hatch.

---

## 9. Очередь правил сделать bitset + ring queue

Сейчас `processRules` работает со слайсом строк:

```go
queue []string
ruleName := queue[0]
queue = queue[1:]
queue = append(queue, ...)
```

и отдельно считает `seenInTurn map[string]int`.

Лучше:

```go
type RuleQueue struct {
    queued bitset
    ring   []RuleID
}
```

При добавлении:

```go
if !queued.Has(ruleID) {
    queued.Set(ruleID)
    ring.Push(ruleID)
}
```

Это убирает дубликаты, строки и лишние проверки.

---

## 10. `PollTask` должен быть O(1), а не scan

В memory store сейчас `PollTask` проходит по всем task execution и ищет первый pending.

Для production store нужно:

```go
pendingQueue map[ExecutionID][]TaskID
taskByID     map[TaskID]*ActivityTask
taskDedup    map[DedupKey]TaskID
```

Или в SQL:

```sql
CREATE INDEX ON tasks (execution_id, status, available_at, seq);
CREATE UNIQUE INDEX ON tasks (execution_id, rule_name, activity_name, idempotency_key);
```

# P2 — надёжность ближе к Temporal

## 11. Сделать transaction обязательным для production

Сейчас `withStoreTransaction` использует транзакцию только если store реализует `TransactionalStore`; иначе просто выполняет функцию без transaction.

Для memory store это нормально, но для production нужно разделить:

```go
MemoryStore       // demo/dev
DurableStore      // обязательно transactional
```

И запретить production mode без transaction.

Особенно важно атомарно делать:

```text
AppendHistory
SaveExecution
EnqueueTask
UpdateTask
```

Иначе можно получить состояние: activity поставлена в очередь, а history не записана, или наоборот.

---

## 12. Добавить outbox/inbox модель

Для уровня Temporal нужно, чтобы внешние эффекты были устойчивы к crash/retry.

Сейчас activity scheduling уже имеет idempotency через `FindTask`, `NextTaskSeq` и `idempotencyKey`.

Но нужно усилить:

```text
ActivityScheduled пишется в history
Task создаётся в outbox
Worker lease берёт task
ActivityCompleted пишется в history
Result применяется только после history event
```

Ключевая идея: внешний эффект не должен зависеть от того, умер процесс между `UpdateTask` и `SaveExecution`.

---

## 13. Lease/heartbeat/retry должны быть частью Store API

Worker уже пытается вызвать опциональный:

```go
RecoverExpiredLeases(ctx, executionID, leaseTTL)
```

но это не часть основного `Store` интерфейса.

Нужно явно добавить:

```go
PollTaskWithLease(ctx, executionID, workerID, leaseTTL)
HeartbeatTask(ctx, taskID, workerID)
RecoverExpiredLeases(ctx, executionID)
CompleteTask(ctx, taskID, result)
FailTask(ctx, taskID, error)
```

И хранить:

```go
LockedBy
LockedUntil
Attempt
MaxAttempts
NextAttemptAt
```

---

## 14. Все nondeterministic операции — только через history

Сейчас используются `time.Now().UTC()` в runtime/store. Например, при старте execution и сохранении.

Для надёжного replay нужно:

```go
Clock interface {
    Now() time.Time
}
```

Но лучше: время, random, UUID, timer firing — всё записывать в history.

```text
TimerScheduled
TimerFired { firedAt }
SideEffectRecorded { value }
```

Replay не должен заново спрашивать текущее время.

---

## 15. Версионирование DSL и compiled plan

В `Execution` уже есть `Version`, но это версия сохранения execution, а не версия workflow definition.

Нужно добавить:

```go
ModuleHash string
CompilerVersion string
PlanVersion string
```

В `ExecutionStarted` записывать:

```json
{
  "domain": "...",
  "moduleHash": "...",
  "compilerVersion": "..."
}
```

При replay использовать тот же compiled module или проверять совместимость.

# P3 — битовые маски в compiler/runtime

## 16. Скомпилировать все dependency indexes в `[]bitset`

Сейчас compiler строит строковые индексы:

```go
SignalIndex map[string][]string
ChangedIndex map[string][]string
TimerIndex map[string][]string
WriteTargetIndex map[string][]string
```

Это хорошо для диагностики, но runtime должен получить:

```go
type CompiledPlan struct {
    FieldRules  []bitset
    SignalRules []bitset
    AtomRules   []bitset
    AtomDeps    []bitset
    AtomClaims  []bitset
}
```

Строковые индексы оставить только для debug/query.

---

## 17. Разделить bool-атомы и value-атомы

Сейчас `fastAtom` бывает:

```go
predicate
computed
fact
```

и все они приводятся к bool-состоянию через `truthy`.

Лучше:

```go
BoolAtom:
  active bitset

ValueAtom:
  values map[AtomID]Value
  present bitset
```

Например:

```go
computed riskScore: Int
computed riskHigh: Bool = riskScore > 80
```

`riskHigh` — bitset, `riskScore` — value map.

---

## 18. Не хранить false computed/fact в map

Сейчас `syncExecutionFromAtoms` при false-атомах может записывать `false` в `Computed` и `FactValue{True:false}` в `Facts`.

Если цель — масштаб, лучше:

```text
отсутствует в map + бит не активен = false / none
```

То есть map хранит только нестандартные значения, а bool-состояние — в битовой маске.

---

## 19. Ограничить DNF-взрыв в `or/and`

Сейчас `andConditions` делает декартово произведение clauses:

```go
for _, l := range left.clauses {
    for _, r := range right.clauses {
        ...
    }
}
```

Для сложных выражений это может взорваться по памяти.

Нужно добавить:

```go
MaxFastClauses
```

Если больше лимита — fallback в slow или BDD-like representation.

---

## 20. Strict fast runtime сделать production default

У вас уже есть `EnableStrictFastRuntime`, который пересобирает plan и возвращает ошибки, если выражение не поддержано fast-runtime.

Для production режима лучше:

```go
WithStrictFastRuntime()
```

по умолчанию включать в benchmark/high-scale mode. Иначе часть выражений уедет в slow path, а скорость станет непредсказуемой.

# Итоговый roadmap

## Самый высокий ROI

1. Перенести `activeAtoms` из `fastPlan.states` в `Execution`.
    
2. Заменить `bitset.ids()` на zero-allocation iterator через `math/bits`.
    
3. Ввести `FieldID/RuleID/AtomID/SignalID`.
    
4. Заменить `changed map[string]struct{}` на `bitset`.
    
5. Перевести `Context/Computed/Facts` на `present bitset + bool bitset + values map[uint32]Value`.
    
6. Сделать настоящий replay из history.
    
7. Сделать transaction/outbox обязательными для durable store.
    
8. Сделать task polling/lease/dedup индексированными.
    

## После этих изменений hot path будет выглядеть так

```go
func (p *Plan) OnChanged(exec *Execution, dirtyFields bitset) {
    dirtyAtoms := p.fieldAtoms.OrMany(dirtyFields)
    changedAtoms := p.Recompute(exec, dirtyAtoms)

    candidateRules := bitset{}
    candidateRules.OrMany(p.fieldRules, dirtyFields)
    candidateRules.OrMany(p.atomRules, changedAtoms)

    p.ProcessRules(exec, candidateRules)
}
```

А значения будут доставаться так:

```go
v, ok := exec.Values[fieldID]
```

или для bool:

```go
ok := exec.BoolValues.Has(fieldID)
```

Это и есть нужное направление: **битовые маски для всего, что является множеством/активностью/готовностью, и `map[uint32]Value` только для редких детальных значений**.

Главный вывод: у вас уже есть правильное ядро (`fastPlan + bitset`), но оно пока обёрнуто в string/map/any runtime. Чтобы приблизиться к Temporal по надёжности и к O(1) по скорости, нужно сделать compiled-ID runtime, durable event history replay и вынести все boolean-состояния в bitset.
